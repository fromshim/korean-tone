---

Claude Code의 기계어와 내부 용어의 남발, 안 좋은 가독성.. 지겨우셨나요?  
한국인이 읽기에 적합하지 않은 클로드의 답변을 교정하기 위해, korean-tone을 만들어버렸습니다.

계획·구현 설명, 리뷰, 체크리스트, 연구노트, 선택지의 딱딱한 번역투를 걷어내되 코드와
정확성은 그대로 둡니다. 같은 내용을 `easy`·`mz` 모드로 말투만 바꿔 들을 수도 있습니다.

---

**말투를 바꾸는 스킬처럼 보이지만, 하는 일은 상황을 판별하는 것입니다.**

`야르`가 나왔다는 건 모델이 "이 변경 하나가 뒤의 여러 일까지 푼다"고 판단했다는 뜻입니다.
`멘헤라`는 "막아줄 장치가 없다", `에바`는 "규모가 과하다"는 판정입니다. 유행어가 감정
장식이 아니라 판정 결과입니다.

평소에는 `default`가 조용히 돌면서 번역투만 걷어냅니다. 아래 유행어는 `mz`를 켤 때만
나옵니다.

## ✍️ 이렇게 바뀝니다

### 1. 기술 용어는 지우지 않고 뜻을 풀어 씁니다

```diff
- handler가 stub이었다.
+ handler는 웹훅만 받고 저장하지 않았어요. 함수의 뼈대만 있고 실제 처리가 빠져 있었어요.
```

용어를 다른 말로 바꾸는 것이 아니라, 남겨둔 채 뜻을 한 문장 덧붙입니다.

### 2. 코드에서 찾아야 할 이름은 건드리지 않습니다

```diff
- client_id가 틀렸습니다.
+ client_id가 잘못됐어요. 인스타 전용 앱 ID가 들어갈 자리에 메타 앱 ID를 썼어요.
```

`client_id`는 그대로 남습니다. **저장소에서 다시 찾아야 할 이름(함수·파일·필드·커밋)은
좌표이므로 바꾸지 않습니다.** 이를 "고객 식별자"로 옮기면 사용자가 실제 코드를 찾기
어려워집니다.

### 3. 내부 작업 용어는 답변에서 걷어냅니다

```diff
- [충돌 A] OCR 품질 게이트를 어떻게 처리할까요?
-   (현재: 'acceptable verbatim quality' — 측정 불가 지적)
+ AI가 손글씨를 잘 읽는지 언제 확인할까요?

- 온톨로지를 어떻게 고칠까요? (QA: auth_provider 누락 지적)
+ 데이터 구조를 정리할까요?

- 수렴 제안 2건(인젝션 한 줄 제약 + 디자인 육안 승인 기준)을 적용할까요?
+ 추가 지침은 한 줄로 제한하고, 디자인은 결과물을 직접 본 뒤 승인하도록 할까요?
```

`수렴 제안`, `AC7`, `이터레이션` 같은 말은 Claude가 작업을 관리하려고 쓰는 표현입니다.
사용자의 결정에 필요하지 않다면 답변에 드러내지 않습니다. 다만 내용을 줄이지는 않아요.

### 4. 그 밖의 번역투도 함께 걷어냅니다

```diff
- 이 함수에 대해 리팩토링을 진행하겠습니다.
+ 이 함수를 리팩토링할게요.

- **재시도 정책** — 3회까지 지수 백오프로 재시도하며, 그 뒤에는 DLQ로 보냅니다.
+ **재시도 정책**: 3회까지 지수 백오프로 재시도하고, 그 뒤에는 DLQ로 보냅니다.
```

수동태와 명사화를 동사로 풀고, 영어 글쓰기에서 넘어온 em dash 습관을 콜론과 마침표로
바꿉니다. 전체 목록은 [`references/translationese.md`](references/translationese.md)에
있습니다.

## 🎭 같은 내용, 세 가지 말투

| 모드 | 명령 |
|---|---|
| **default** | `/korean-tone:default` |
| **easy** | `/korean-tone:easy` |
| **mz** | `/korean-tone:mz` |

**default**

> 에이전트 3개로 검토해보니 `resolveConfig()`가 설정 읽기, 환경 변수 병합, 검증까지 모두
> 담당하고 있습니다. 조건문이 네 단계로 중첩되어 있고 같은 fallback 로직도 세 곳에
> 중복되어 있어 구조를 개선할 필요가 있습니다.
>
> 파싱·병합·검증 단계를 분리하고, fallback 처리는 `resolveFallback()` 하나로 모으는 것을
> 권장합니다. 이렇게 바꾸면 각 단계의 테스트 범위가 명확해지고 새로운 환경을 추가할 때
> 수정해야 하는 곳도 한 군데로 줄어듭니다.
>
> 우선 `mergeEnv()`를 분리한 뒤 기존 호출부를 하나씩 옮기면 됩니다.

**easy**

> 에이전트 3개로 코드를 살펴봤어요. `resolveConfig()` 한 함수가 세 가지 일을 같이 하고
> 있어요. 설정을 읽는 일, 환경 변수를 합치는 일, 값이 올바른지 확인하는 일이에요.
>
> 여기서 두 가지가 문제예요. 먼저 조건문이 네 단계로 겹쳐 있어요. 그래서 어떤 조건에서
> 어떤 값이 나오는지 따라가기 어려워요. 그리고 값이 없을 때 대신 쓰는 처리(fallback)가
> 세 곳에 똑같이 적혀 있어요. 한 곳을 고치면 나머지 두 곳도 같이 고쳐야 해요.
>
> 세 가지 일을 따로 떼면 돼요. 읽기, 합치기, 확인하기를 각각 분리하고 fallback 처리는
> `resolveFallback()` 하나에 모아요. 그러면 각 단계를 따로 시험할 수 있어요. 새 환경을
> 추가할 때 고칠 곳도 한 군데로 줄어요.
>
> `mergeEnv()`를 떼어내는 것부터 시작하면 돼요. 그다음 이 함수를 부르던 곳을 하나씩
> 옮기면 돼요.

**mz**

> 에이전트 3개 돌려보니 `resolveConfig()` 하나가 설정 읽기부터 환경 변수 병합, 검증까지
> 다 먹고 있어요. 조건문은 네 겹이고 같은 fallback이 세 군데 복붙이라 이 구조 개밤티예요;;
>
> 나같경 파싱·병합·검증부터 떼고 fallback은 `resolveFallback()` 하나로 모으는 쪽이요.
> 그러면 테스트 경계가 또렷해지고 새 환경 추가할 때 고칠 곳도 한 군데로 줄어요. 하나
> 정리했는데 뒤 문제까지 같이 풀리는 게 ㄹㅇ 야르예요
>
> 일단 `mergeEnv()`부터 빼고 기존 호출을 하나씩 옮기면 돼요 아자스!

세 답변의 높임이 같습니다. `mz`는 말투 층이 아니라 표현 층이라, 사용자가 반말로 물으면
`개밤티예요`가 `개밤티`로 바뀔 뿐 나머지는 그대로 붙습니다. 일반 문장은 평소처럼
마침표를 쓰고, `개밤티예요;;`나 `아자스!`처럼 MZ 표현이 문장을 끝낼 때만 붙이지 않습니다.

## 🧩 유행어를 부품으로 분해했습니다

유행어를 완성된 문구로 외우게 하면 두 가지가 망가집니다. 상황이 조금만 달라져도 어색해지고,
같은 문구가 계속 돌아옵니다.

`mz` 모드는 표현을 부품으로 봅니다.

```text
[도입] + [사실 문장] + [강조·정도] + [의미 코어] + [어미·꼬리]
```

`ㄹㅇ개밤티임;;`은 하나의 단어가 아니라 조합된 결과입니다.

```text
ㄹㅇ  +  개  +  밤티  +  임  +  ;;
강조    정도   의미    어미   꼬리
```

의미 코어마다 언제 쓰는지가 정해져 있습니다.

| 코어 | 쓰는 상황 |
|---|---|
| `야르` | 변경 하나로 뒤의 여러 일까지 같이 풀릴 때 |
| `개좋` | 한 가지 장점이나 결과가 확실히 좋을 때 |
| `멘헤라` | 같은 문제가 반복되고 자동 방어선도 없을 때 |
| `늙크크` | deprecated API, legacy 경로를 끌고 갈 때 |
| `밤티` | 구조나 화면이 못생기고 엉켜 개선이 필요할 때 |
| `에바` | 비용·복잡도·상황이 과해 감당하기 어려울 때 |

헷갈리는 짝은 질문 하나로 가릅니다. 오래된 게 핵심이면 `늙크크`, 엉킨 게 핵심이면 `밤티`.
규모가 과하면 `에바`, 막아줄 장치가 없으면 `멘헤라`.

`샤갈`은 코어가 아니라 감탄사라 굴절하지 않습니다. `샤갈이야`나 `좀 샤갈`처럼 쓰지 않고
부호로만 강도를 조절합니다. `나같경`은 문장의 첫 토큰으로만 쓰고, 맨 앞에 둘 수 없으면
생략합니다.

그래서 같은 조합이 반복되지 않습니다. 밀도는 올리되 골격은 매번 흩습니다.

## 🔒 유행어를 빼면 원래 답이 남습니다

`mz` 모드에는 지켜야 할 조건이 하나 있습니다. **유행어를 전부 지워도 사실, 제안,
인과관계가 모두 남아야 합니다.**

그래서 `mz`는 요청을 새로 풀거나 내용을 요약하지 않습니다. 먼저 `default` 답변을 만들고
그 위에 표현을 얹습니다. 코드 식별자와 버전, 수량, 조건, 부정은 그대로 둡니다. 원문에 없는
근거나 경험을 말투를 바꾸면서 만들지 않습니다.

높임도 바꾸지 않습니다. 사용자가 반말이면 `밤티`, 해요체면 `밤티예요`로 코어를
굴절시킵니다.

## ⚙️ 훅 네 개가 하는 일

말투를 프롬프트로 부탁하지 않습니다. 훅 네 개가 규칙을 심고 결과를 되잡습니다.

| 훅 | 하는 일 |
|---|---|
| `SessionStart` | 세션이 열릴 때 규칙을 넣습니다 |
| `UserPromptSubmit` | 요청마다 현재 모드를 다시 알려줍니다 |
| `SubagentStart` | **하위 에이전트에게도 같은 규칙을 전파합니다** |
| `PostToolUse` | **방금 저장한 글에서 번역투를 되잡습니다** |

뒤의 둘이 이 스킬의 차이입니다. 서브에이전트만 말투가 튀는 문제를 구조로 막고, 교정기가
자기 출력에도 걸립니다.

린터 규칙은 국립국어원의 번역투 연구, 토스 테크니컬 라이팅 가이드, 이오덕의
『우리글 바로쓰기』를 참고해 정리했습니다. 기계적으로 판별할 수 있는 `~에 의해`, 이중 피동,
`~에 있어서`, `그녀`는 `error`로 봅니다. 문맥과 빈도를 함께 봐야 하는 `~를 통해`, `것이다`,
메타 담화는 `warn`으로 둡니다.

코드 블록과 인라인 코드, URL은 검사하지 않습니다. 파일에 `<!-- tone-lint: off -->`를 넣으면
그 파일은 통째로 건너뜁니다. 린터는 저장을 막지 않고, 저장이 끝난 뒤 다듬을 표현만
알려줍니다.

## 📦 설치

### 플러그인으로 설치

Claude Code에서만 동작합니다. 설치한 뒤 새 세션을 열면 기본 Korean Tone이 모든 한국어
답변에 적용됩니다. 문서 린터와 `default`·`easy`·`mz` 모드도 함께 설치되며, 추가 설정은
없습니다.

```bash
/plugin marketplace add fromshim/korean-tone
/plugin install korean-tone@fromshim
```

### skills.sh로 설치

Claude Code 외에 Codex, Cursor, Antigravity, Amp, Gemini CLI 등 여러 에이전트에 설치됩니다.
작성 규칙만 적용되고 훅은 등록되지 않으므로, 자동 검사를 쓰려면
[`hooks/register-hook.py`](hooks/README.md)를 직접 실행합니다.

```bash
npx skills add fromshim/korean-tone
```

## ⏱️ 언제 동작하나

### 플러그인: 설치 직후부터 매 답변

새 세션을 시작할 때 기본 규칙을 불러오고, 질문을 보낼 때마다 현재 모드를 짧게 다시
알려줍니다. 그래서 사용자가 스킬을 따로 부르지 않아도 한국어 답변에 계속 적용됩니다.

말투를 바꾸고 싶을 때만 위의 말투 모드 명령(`/korean-tone:default`·`easy`·`mz`)을
씁니다. 바꾼 모드는 같은 세션에서 계속 유지됩니다. `/clear`나 대화 압축 뒤에도 유지되고, 새 세션을
시작하면 `default`로 돌아갑니다.

체크리스트나 연구노트처럼 문서별 규칙까지 직접 부르고 싶다면
`/korean-tone:korean-tone`을 쓸 수 있습니다.

### skills.sh: 필요한 한국어 작업에서 스킬 적용

`npx skills`로 설치하면 `/korean-tone`으로 직접 부르거나, "어투 교정", "말투 자연스럽게",
"번역투 고쳐"처럼 요청할 수 있습니다. 항상 적용되는 훅과 말투 모드는 플러그인 설치에서만
제공합니다.

### 린터 훅: 조건이 맞을 때만 돕니다

플러그인으로 설치했다면 아래를 **모두** 만족할 때 검사합니다.

- Claude가 `Write` 또는 `Edit`로 파일을 저장했을 때
- 확장자가 `.md`, `.mdx`, `.markdown`일 때
- 저장한 내용에 한글이 있을 때
- 파일에 `<!-- tone-lint: off -->`가 없을 때

검사에서 빼는 것: 코드 블록, 인라인 코드, URL, 링크 주소.
`Edit`은 바뀐 부분만 검사하고, 줄 번호는 파일 기준으로 알려줍니다.

`tone-linter`는 파일로 저장된 내용만 검사합니다. 대화 답변의 말투는 앞의 기본 말투 훅이
맡습니다.

## 💸 토큰을 얼마나 쓰나

플러그인은 출력을 만든 뒤 다시 고치는 방식이 아닙니다. 세션 시작에 짧은 기본 규칙을 넣고,
Claude가 처음부터 그 말투로 문장을 만듭니다.

| 항목 | 크기 | 로드 시점 |
|---|---:|---|
| `rules/default.md` | 약 1,900 토큰 | 세션 시작·재개·대화 압축 뒤 |
| 모드 알림 (`default`·`easy`) | 약 70 토큰 | 질문을 보낼 때마다 |
| 모드 알림 (`mz`) | 약 430 토큰 | 질문을 보낼 때마다 |
| 하위 에이전트 지시문 | 약 140 토큰 | 하위 에이전트가 뜰 때마다 |
| `rules/easy.md` | 약 310 토큰 | `/korean-tone:easy`로 켤 때 한 번 |
| `rules/mz.md` | 약 3,900 토큰 | `/korean-tone:mz`로 켤 때 한 번 |
| 문서별 스킬 | 약 450 토큰 | 관련 문서를 다룰 때만 |
| `references/*` | 파일마다 약 1,100~2,400 토큰 | 해당 문서 규칙이 필요할 때만 |

매 질문의 짧은 모드 알림은 `caveman`과 같은 방식으로 말투가 흐트러지지 않게 붙잡는
비용입니다. 규칙 전체를 매번 다시 넣지는 않습니다.

`mz`가 가장 비쌉니다. 켤 때 부품 규칙을 한 번 넣고, 그 뒤로는 질문마다 약 430 토큰짜리
요약을 붙입니다. 부품 조합은 문구 암기보다 알려줄 것이 많아서 알림도 깁니다. `default`로
두면 질문당 약 70 토큰입니다.

하위 에이전트에는 규칙 전문 대신 두 줄만 넣습니다. 에이전트를 여럿 띄우면 프롬프트마다
곱해지기 때문입니다. 놓친 번역투는 `tone-linter`가 파일 저장 시점에 잡습니다.

`tone-linter`는 로컬 파이썬 스크립트라 실행 자체에는 토큰을 쓰지 않습니다. 번역투를 찾았을
때만 짧은 지적 내용이 대화에 들어옵니다.

표의 숫자는 글자 수로 잡은 추정치입니다. 실제 값은 모델의 토크나이저에 따라 달라집니다.

## 🚧 선 넘지 않기

말맛을 끄는 자리를 규칙으로 정해 뒀습니다.

- 보안 경고, 되돌릴 수 없는 작업, 손실 가능성, 오류 원문은 유행어보다 정확성을 우선합니다
- 위험한 실행이나 심각한 경고를 `아자스!`, `ㅋㅋ`로 가볍게 봉합하지 않습니다
- 코드와 명령어, 식별자, URL, 오류 메시지, 인용문 안에는 댓글체를 섞지 않습니다
- 커밋과 PR, 공식 문서 본문은 사용자가 명시적으로 요청할 때만 바꿉니다
- 욕설과 비하 표현이 사람을 향하지 않습니다

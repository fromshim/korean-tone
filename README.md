Claude Code의 기계어와 내부 용어의 남발, 안 좋은 가독성.. 지겨우셨나요?  
한국인이 읽기에 적합하지 않은 클로드의 답변을 교정하기 위해, korean-tone을 만들어버렸습니다.

계획·구현 설명, 리뷰, 체크리스트, 연구노트, 선택지의 딱딱한 번역투를 걷어내되 코드와
정확성은 그대로 둡니다. 같은 내용을 `easy`·`mz` 모드로 말투만 바꿔 들을 수도 있습니다.

## ✍️ 이렇게 바뀝니다

### 1. 기술 용어는 지우지 않고 뜻을 풀어 씁니다

```diff
- handler가 stub이었다.
+ handler는 웹훅만 받고 저장하지 않았어요. 함수의 뼈대만 있고 실제 처리가 빠져 있었어요.
```

용어를 다른 말로 바꾸는 것이 아니라, 남겨둔 채 뜻을 한 문장 덧붙입니다.

### 2. 코드에서 찾아야 할 이름은 건드리지 않습니다

```diff
- client_id가 틀렸습니다.
+ client_id가 잘못됐어요. 인스타 전용 앱 ID가 들어갈 자리에 메타 앱 ID를 썼어요.
```

`client_id`는 그대로 남습니다. **저장소에서 다시 찾아야 할 이름(함수·파일·필드·커밋)은
좌표이므로 바꾸지 않습니다.** 이를 "고객 식별자"로 옮기면 사용자가 실제 코드를 찾기
어려워집니다.

### 3. 내부 작업 용어는 답변에서 걷어냅니다

```diff
- [충돌 A] OCR 품질 게이트를 어떻게 처리할까요?
-   (현재: 'acceptable verbatim quality' — 측정 불가 지적)
+ AI가 손글씨를 잘 읽는지 언제 확인할까요?

- 온톨로지를 어떻게 고칠까요? (QA: auth_provider 누락 지적)
+ 데이터 구조를 정리할까요?

- 수렴 제안 2건(인젝션 한 줄 제약 + 디자인 육안 승인 기준)을 적용할까요?
+ 추가 지침은 한 줄로 제한하고, 디자인은 결과물을 직접 본 뒤 승인하도록 할까요?
```

`수렴 제안`, `AC7`, `이터레이션` 같은 말은 Claude가 작업을 관리하려고 쓰는 표현입니다.
사용자의 결정에 필요하지 않다면 답변에 드러내지 않습니다. 다만 내용을 줄이지는 않아요.

### 4. 대시로 잇지 않고 끊어 씁니다

```diff
- **재시도 정책** — 3회까지 지수 백오프로 재시도하며, 그 뒤에는 DLQ로 보냅니다.
+ **재시도 정책**: 3회까지 지수 백오프로 재시도하고, 그 뒤에는 DLQ로 보냅니다.

- 마이그레이션은 두 단계입니다 — 먼저 컬럼을 추가하고, 배포 뒤에 백필합니다.
+ 마이그레이션은 두 단계입니다. 먼저 컬럼을 추가하고, 배포한 뒤에 백필합니다.
```

영어 글쓰기의 em dash 습관이 그대로 넘어온 자리입니다. 라벨 뒤에는 콜론을 쓰고, 문장을
잇는 자리에서는 문장을 끊습니다. 표나 목록의 구분자로 쓰는 대시는 그대로 둡니다.

한 문단에 사실을 서너 개 담았을 때도 끊어 줍니다.

```diff
- 캐시는 1시간 유지되고 이미지 URL 수명도 1시간이라 둘이 겹치면 만료된 주소를 내려주게 되는데, 이때 브라우저는 403을 받습니다.
+ 캐시는 1시간 유지되는데, 이미지 URL 수명도 1시간입니다.
+ 둘이 겹치면 만료된 주소를 내려주고, 브라우저는 403을 받습니다.
```

### 5. 기본적인 번역투도 함께 걷어냅니다

```diff
- 이 함수에 대해 리팩토링을 진행하겠습니다.
+ 이 함수를 리팩토링할게요.

- 입력값 검증이 수행되며, 수정이 이루어졌습니다.
+ 여기서 입력값을 검증했고, 문제도 고쳤어요.
```

## 🎭 같은 내용, 세 가지 말투

기본 말투 외에 모드 두 개를 더 담았습니다. 어떤 모드든 사실·순서·설명량은 그대로 두고
말투만 바꿉니다.

| 모드 | 명령 | 말투 |
|---|---|---|
| **default** | `/korean-tone:default` | 딱딱함만 걷어낸 기본 말투 |
| **easy** | `/korean-tone:easy` | 무슨 일인지 → 왜 그런지 → 어떻게 하면 되는지 순서로, 중간 단계를 건너뛰지 않고 하나하나 설명 |
| **mz** | `/korean-tone:mz` | 인스타 댓글체. 어미·반응만 바꾸고 내용은 그대로 |

같은 설명이 모드에 따라 이렇게 달라집니다.

**default**

> `legacyInit()`은 2.4부터 deprecated예요. 호환성 때문에 당장 뺄 수는 없지만,
> 새로 호출하는 곳은 막아야 해요. 래퍼 하나로 모아두고 사용처를 줄여가면 돼요.

**easy**

> `legacyInit()`은 이제 쓰지 않기로 한 함수예요(deprecated). 오래된 코드가 아직 이
> 함수를 쓰고 있어서 바로 지울 수는 없어요. 지우면 그 코드들이 멈추거든요.
> 그래서 두 가지를 하면 돼요. 먼저 새 코드에서는 이 함수를 못 쓰게 막아요.
> 그다음 이미 쓰고 있는 곳을 하나씩 줄여가요.

**mz**

> `legacyInit()`은 2.4부터 deprecated야
> 호환성 때문에 당장 못 빼도 신규 호출은 막아야 해
> 래퍼 하나로 모으고 사용처를 줄여가면 돼
> 여기 로직은 늙크크

easy는 용어를 쉬운 말로 먼저 풀고 원래 이름을 괄호로 남깁니다. mz는 강조·반응 표현을
상황에 맞을 때만 조합하고, 보안 경고나 오류 원문처럼 정확해야 하는 곳은 건드리지 않습니다.

위 mz 예시는 짧은 단답이라 반응을 하나만 씁니다. 진단·추천·이점·첫 실행이 모두 있는 긴
답변은 아래 기준을 따릅니다.

### default 답변 위에 MZ 말투를 얹습니다

MZ 모드는 요청을 처음부터 다시 해석하지 않습니다. 먼저 default 답변의 사실·진단·제안·이점과
실행 순서를 잠근 다음, 그 위에 어미와 반응만 바꿉니다. 아래 쌍을 이 변환의 대표 기준으로
씁니다.

**default**

> 에이전트 3개로 검토해보니 `resolveConfig()`가 설정 읽기, 환경 변수 병합, 검증까지 모두
> 담당하고 있습니다. 조건문이 네 단계로 중첩되어 있고 같은 fallback 로직도 세 곳에
> 중복되어 있어 구조를 개선할 필요가 있습니다.
>
> 파싱·병합·검증 단계를 분리하고, fallback 처리는 `resolveFallback()` 하나로 모으는 것을
> 권장합니다. 이렇게 바꾸면 각 단계의 테스트 범위가 명확해지고 새로운 환경을 추가할 때
> 수정해야 하는 곳도 한 군데로 줄어듭니다.
>
> 우선 `mergeEnv()`를 분리한 뒤 기존 호출부를 하나씩 옮기면 됩니다.

**mz**

> 에이전트 셋 돌려서 검토해보니 `resolveConfig()` 하나가 설정 읽기부터 환경 변수 병합,
> 검증까지 다 먹고 있어
> 조건문 네 겹에 같은 fallback도 세 군데 복붙이라 여기 구조 ㄹㅇ개밤티임;;
>
> 나같경 파싱·병합·검증부터 떼고 fallback은 `resolveFallback()` 하나로 모아
> 그러면 테스트 경계가 또렷해지고 새 환경 추가할 때 고칠 곳도 한 군데로 줄어
> 하나 정리했는데 뒤 문제까지 같이 풀리는 게 ㄹㅇ야르
>
> 일단 `mergeEnv()`부터 빼고 기존 호출을 하나씩 옮기면 돼 아자스!

`밤티`가 구체적인 중첩·중복 근거를 지우지 않고, `야르`도 테스트와 수정 범위라는 두 이점을
말한 뒤에 나오는 것이 핵심입니다. MZ 표현을 전부 걷어내도 default 답변의 의미가 남아야
합니다.

## ⚙️ 설치하면 모든 한국어 답변에 적용됩니다

플러그인 설치 시 세 층이 함께 작동합니다.

| 구성 | 역할 | 작동 방식 |
|---|---|---|
| **기본 말투 훅** | 매 답변의 말투를 정합니다 | 세션 시작에 규칙을 넣고, 질문마다 현재 모드를 다시 알려줍니다. |
| **문서별 스킬** | 문서 형식까지 다듬습니다 | 체크리스트·연구노트·선택지에 맞는 세부 규칙을 불러옵니다. |
| **자동 점검(`tone-linter`)** | 놓친 표현을 알려줍니다 | 한국어 `.md`를 저장할 때 번역투를 검사합니다. |


린터 규칙은 국립국어원의 번역투 연구, 토스 테크니컬 라이팅 가이드, 이오덕의
『우리글 바로쓰기』를 참고해 정리했습니다.

규칙은 두 등급으로 나눕니다. 기계적으로 판별할 수 있는 것은 `error`로 봅니다.
`~에 의해`, 이중 피동, `~에 있어서`, `그녀` 같은 표현이 여기 듭니다.
문맥과 빈도를 함께 봐야 하는 `~를 통해`, `것이다`, 메타 담화는 `warn`으로 둡니다.

코드 블록, 인라인 코드, URL은 검사하지 않습니다.
파일에 `<!-- tone-lint: off -->`를 넣으면 그 파일은 통째로 건너뜁니다.

린터는 파일 저장을 막지 않습니다. 저장이 끝난 뒤 다듬을 표현만 알려줍니다.

## 📦 설치

### 플러그인으로 설치

Claude Code에서만 동작합니다. 설치한 뒤 새 세션을 열면 기본 Korean Tone이 모든 한국어
답변에 적용됩니다. 문서 린터와 `default`·`easy`·`mz` 모드도 함께 설치되며, 추가 설정은
없습니다.

```bash
/plugin marketplace add fromshim/korean-tone
/plugin install korean-tone@fromshim
```

### skills.sh로 설치

Claude Code 외에 Codex, Cursor, Antigravity, Amp, Gemini CLI 등 여러 에이전트에 설치됩니다.
작성 규칙만 적용되고 훅은 등록되지 않으므로, 자동 검사를 쓰려면
[`hooks/register-hook.py`](hooks/README.md)를 직접 실행합니다.

```bash
npx skills add fromshim/korean-tone
```

## ⏱️ 언제 동작하나

### 플러그인: 설치 직후부터 매 답변

새 세션을 시작할 때 기본 규칙을 불러오고, 질문을 보낼 때마다 현재 모드를 짧게 다시
알려줍니다. 그래서 사용자가 스킬을 따로 부르지 않아도 한국어 답변에 계속 적용됩니다.

말투를 바꾸고 싶을 때만 위의 말투 모드 명령(`/korean-tone:default`·`easy`·`mz`)을
씁니다. 바꾼 모드는 같은 세션에서 계속 유지됩니다. `/clear`나 대화 압축 뒤에도 유지되고, 새 세션을
시작하면 `default`로 돌아갑니다.

체크리스트나 연구노트처럼 문서별 규칙까지 직접 부르고 싶다면
`/korean-tone:korean-tone`을 쓸 수 있습니다.

### skills.sh: 필요한 한국어 작업에서 스킬 적용

`npx skills`로 설치하면 `/korean-tone`으로 직접 부르거나, "어투 교정", "말투 자연스럽게",
"번역투 고쳐"처럼 요청할 수 있습니다. 항상 적용되는 훅과 말투 모드는 플러그인 설치에서만
제공합니다.

### 린터 훅: 조건이 맞을 때만 돕니다

플러그인으로 설치했다면 아래를 **모두** 만족할 때 검사합니다.

- Claude가 `Write` 또는 `Edit`로 파일을 저장했을 때
- 확장자가 `.md`, `.mdx`, `.markdown`일 때
- 저장한 내용에 한글이 있을 때
- 파일에 `<!-- tone-lint: off -->`가 없을 때

검사에서 빼는 것: 코드 블록, 인라인 코드, URL, 링크 주소.
`Edit`은 바뀐 부분만 검사하고, 줄 번호는 파일 기준으로 알려줍니다.

`tone-linter`는 파일로 저장된 내용만 검사합니다. 대화 답변의 말투는 앞의 기본 말투 훅이
맡습니다.

## 💸 토큰을 얼마나 쓰나

플러그인은 출력을 만든 뒤 다시 고치는 방식이 아닙니다. 세션 시작에 짧은 기본 규칙을 넣고,
Claude가 처음부터 그 말투로 문장을 만듭니다.

| 항목 | 크기 | 로드 시점 |
|---|---:|---|
| `rules/default.md` | 약 1,900 토큰 | 세션 시작·재개·대화 압축 뒤 |
| 현재 모드 알림 | 약 80~120 토큰 | 질문을 보낼 때마다 |
| 문서별 스킬 | 약 500 토큰 이하 | 관련 문서를 다룰 때만 |
| `references/*` | 파일마다 약 1,600~2,700 토큰 | 해당 문서 규칙이 필요할 때만 |

매 질문의 짧은 모드 알림은 `caveman`과 같은 방식으로 말투가 흐트러지지 않게 붙잡는
비용입니다. 규칙 전체를 매번 다시 넣지는 않습니다.

`tone-linter`는 로컬 파이썬 스크립트라 실행 자체에는 토큰을 쓰지 않습니다. 번역투를 찾았을
때만 짧은 지적 내용이 대화에 들어옵니다.

## 🧪 평가

규칙을 바꾼 뒤에는 같은 사례로 다시 확인합니다.

- **호출 여부**: [`evals/`](evals)의 질의 10개로, 문서별 스킬이 필요할 때만 호출되는지 봅니다.
- **교정 품질**: [`evals/quality-cases.jsonl`](evals/quality-cases.jsonl)의 사례 13개를 [`evals/evaluate_quality.py`](evals/evaluate_quality.py)로 채점합니다. 좌표 보존, 번역투 제거, 과교정을 먼저 거릅니다.
- **사람 검수**: 자연스러움, 정확성, 말투 일치, 과교정 여부는 사람이 1~5점으로 매깁니다. 같은 스크립트의 `--write-review`로 검수표를 만듭니다.

```bash
python3 evals/evaluate_quality.py --outputs <파일>   # 자동 채점
python3 hooks/tone-context.py --selftest             # 항상 적용·모드 전환 점검
python3 hooks/tone-linter.py --selftest              # 린터 자체 점검
```

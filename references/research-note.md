# 요소별 특화 — 설계 결정 기록·연구노트

설계 결정을 기록하거나(ADR), 문제 해결 과정을 정리하는 "연구노트"를 쓸 때의 규칙.
담백한 문어체로, **왜 이렇게 결정했는지**와 **앞으로의 원칙**을 남기는 게 목적이다.

핵심 한 줄: **결정과 근거를 담백하게. 감정·유머·독자 호출 없이, `~다` 평서형으로.**

---

## 보이스

- **`~다` 평서형 문어체.** "~한다 / ~이다 / ~하는 데 있다 / ~해야 안정적이다." 대화체
  (~할게, ~해요)나 격식체(~하겠습니다) 아님.
- **감정·유머·이모지·독자 호출 없음.** "알아보자", "까보자", 밈, 취소선 농담은 블로그용
  (→ `shimmy-tone` 스킬). 여기선 담백하게.
- **핵심 결정·개념은 볼드로 강조.** "판정의 중심은 상태값이 아니라 **비즈니스 날짜 문자열
  하나**이다."
- **정확성 우선.** 실제 함수·파일·식별자·코드를 그대로 쓴다. 필요하면 파일 위치 명시
  ("위치: `MissionEntryModalGate.tsx`").
- 공통 어투 규칙(1부)은 그대로 적용 — 번역투·과한 수동태·한자 과압축은 여기서도 뺀다.

## 구조 템플릿 A — 결정 기록형 (ADR)

이미 내린 결정을 정리할 때. 대부분의 설계 문서가 이 꼴이다. (표준 ADR — Nygard·MADR —
에서 가져온 요소를 반영했다.)

1. **머리말** — ID(선택: `ADR-0014` 식)·작성일·**상태**(제안 / 채택 / 폐기 / **대체됨 →
   새 기록 링크**). ADR은 append-only다 — 결정이 바뀌면 기존 문서를 고치지 말고 **새 기록을
   쓰고 서로 링크**한다.
2. **문제 개요** — 무슨 문제를 왜 다루는가. 배경·기존 증상.
3. **결정 요인(drivers)** — 이 결정을 강제한 힘(제약·품질 요구·마감)을 불릿로. 상황이
   바뀌면 결정을 재평가할 기준이 된다.
4. **결정** — 채택안을 한 문장으로 못 박는다. "판정의 중심은 ~ 하나이다"
5. **검토한 대안** — 고른 것만이 아니라 **안 고른 B·C도 같은 수준에서** 나열하고 각 장단점.
   "왜 A인가"만큼 "왜 B·C가 아닌가"가 문서의 수명을 결정한다.
6. **규칙 / 상세** — 구체 규칙, 경우의 수, 코드 (불릿·표·코드블록)
7. **감수하는 것(트레이드오프)** — 이 결정으로 어려워지는 것·추가되는 리스크. 정당화만
   적지 말고 비용도 적는다. (MADR: "Good, because… / Bad, because…")
8. **적용 범위** — 어디에 동일하게 쓰이는가
9. **재사용 / 적용 원칙** — 앞으로 이런 걸 만들 때 지킬 규칙 (불릿). **거의 항상 넣는다.**

> **가드**: 6번(규칙/상세)이 비대해지면 이건 결정 *기록*이지 설계 *가이드*가 아님을 기억한다.
> 보충 설계 자료는 링크로 빼고, 기록 자체는 독립적으로 이해되게 간결·사실 위주로.

## 구조 템플릿 B — 해결 과정형

시행착오를 거친 버그·이슈 해결을 서사로 남길 때.

1. **제목** — 문제 + 해법 힌트 ("헤더가 새로고침 시 안 보이는 문제: rAF 활용")
2. **문제 발견** — 증상 + **원인** (코드로)
3. **첫 번째 시도** → **결과: 실패/경고** (왜 안 됐는지)
4. **두 번째 시도** → **결과: 실패/경고**
5. **최종 해결** — 코드 + **왜 동작하는가** (단계별 표가 잘 맞음)
6. **해결된 것** — 무엇이 좋아졌는지 불릿

각 시도는 "### 결과:" 소제목으로 성패를 명시한다. 실패한 시도를 지우지 말 것 — 왜 그 길로
안 갔는지가 노트의 가치다.

## 공통 관례

- **코드블록엔 실제 코드 + 인라인 주석.** "// ← 다음 프레임에서 실행" 처럼 핵심 줄을 짚는다.
- **단계별 동작은 표로.** 시점·조건·결과가 있으면 마크다운 표가 읽기 좋다.
- **경우의 수는 불릿로 분해.** "`missionList[0]`이 없음 → 어제 기준 유지" 식으로 조건-결과.
- **마무리는 "적용 원칙" 또는 "정리".** 긴 문서면 핵심을 불릿로 압축해 닫는다.

## 미니 예시 (결정 기록형 발췌)

```
# business date 판정 기준 단일화

## 문제 개요
퀘스트 카드·진입 모달·달성현황은 모두 "오늘 기준"이 필요하다. 문제는 이 "오늘"이
달력 날짜와 항상 같지 않다는 점이다. 새벽 2시 batch로 갱신되므로, `new Date()`의 오늘을
그대로 쓰면 화면마다 다른 결과가 나온다.

## 결정
"오늘 보여줄 퀘스트"를 두 단계로 판정한다.
1. `businessToday`를 계산
2. `mission.date === businessToday`인 미션을 찾음

즉, 판정의 중심은 상태값이 아니라 **비즈니스 날짜 문자열 하나**이다.

## 재사용 원칙
- 달력 날짜로 직접 today를 계산하지 않음
- `getMissionBusinessDate(now, missionList[0] ?? null)`을 먼저 호출
- 미션 존재 여부는 `mission.date === businessToday`로 판정
```

특징: 결정을 한 문장으로 못 박고(**볼드**), 마지막에 "앞으로 이렇게 하라"는 재사용 원칙으로
닫는다. 담백한 `~다`체, 실제 함수명 그대로.
